# Accounts

Open Accounts from the title screen, Settings, or the menu avatar. Add Session accepts a Minecraft Java access token or `token:access-token:uuid`. Identity is verified using Minecraft's official profile service, user permissions, and signed profile before switching. Existing profile actions and account permissions are retained. Switching requires leaving the current world/server.

Session entry is masked before measurement and drawing; text caches receive only the mask. Press Login or Enter to verify. **Remember on this PC is on by default** and encrypts credentials with Windows DPAPI under the current Windows user in `maro/accounts.json`; account secrets are separate from shareable configuration files. Turning Remember off makes the imported account temporary. Info shows public profile details and expiry when available, with no token export. Remove deletes the saved entry. Launcher restores the original account and its services.

**Refresh Token** opens Microsoft refresh-token login. Enter your refresh token and the OAuth client ID that issued it. Public desktop clients with modern UUID IDs use Microsoft's consumers v2 endpoint; legacy 16-digit IDs use the Live desktop token endpoint. The client exchanges Microsoft access for Xbox user authorization, Minecraft XSTS authorization and a Minecraft access token, then verifies the Java profile and permissions before switching. A refresh token cannot be generated from a Minecraft access token.

Imported Microsoft accounts have a **Refresh** button. Login automatically renews a stored Microsoft account when its access token has expired or has less than a minute remaining. Rotated refresh tokens replace the old stored token after a successful verified login. Access and refresh tokens and the issuing client ID are encrypted together; old v1 session-only vaults remain readable. Renewal requires a public-client token accepted for Xbox/Minecraft access; confidential-client tokens requiring a client secret are not supported.

Login and validation run off the render thread. Cancellation prevents a late response from replacing the account. Failed validation or persistence preserves the previous identity. Refreshing an existing account checks its UUID. HTTP redirects are not followed, and service response bodies never enter errors or logs. No launcher/browser token discovery is performed.

Production UI tests: `gradlew.bat build runProductionClientGameTest -PaccountsTestOnly=true`. These use synthetic loopback tokens and test Windows encryption, native entry/clicks, profile verification failures, cancellation, duplicate handling, memory-only storage, deletion, complete launcher-state restoration, and refusal to switch inside a world. Real authenticated Microsoft/Minecraft login requires a user-owned valid token and is not exercised by the fixture.

Protocol references: [Microsoft OAuth refresh](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow), [Xbox token exchange](https://learn.microsoft.com/en-us/gaming/gdk/docs/services/fundamentals/s2s-auth-calls/service-authentication/live-website-authentication), [legacy desktop OAuth](https://learn.microsoft.com/it-it/previous-versions/office/infopath-external/dn631818%28v%3Doffice.15%29). The tests also exercise all four HTTP stages, refresh-token rotation, v1/v2 reload, public-client variants, rejected/cancelled renewal, redirect protection, native masked entry, default saving, removal and small-window layouts.
